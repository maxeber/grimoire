# Brigade and head chef: bounds and guards

This page holds detail behind the controls the [threat model](threat-model.md) names. An edit that weakens a control it names is a removed control.

This page holds the detail behind the threat model's R5, R6 and R7: the bounds on each call the Brigade mod makes through the engine, and the head chef's guards and data. The summary below points into the moved text: [row 15](#row-15) for the mod, [row 16](#row-16) for the head chef, and [the engine calls](#row-15-the-engine-calls-behind-its-write-and-its-tool-call) for each call's bounds. Where the summary and the moved text differ, the moved text holds the detail, and a class holds only what its sentence in the threat model names. Residual risks are named by the threat model's classes and open issues only. Where a row says "the same by others is open", it applies to each such row below: a program the owner runs is the machine's; the same by another plugin, a branch's code, a steered session or any tool from outside input is an open issue of the threat model, and no row loses that status. Each "Accepted class" on this page is a class named in the threat model.

Sources: `brigade/register.tsx`, `brigade/stop.ts`, `skills/head-chef/references/CONTRACT.md` and `skills/head-chef/references/cleanup.md`, ADR 0008 and ADR 0010.

## Summary, part 1: the mod's calls and their bounds

- **Offered only where asked.** The mod's tools are offered only after `/brigade` or a head-chef load, and work only once the mod has offered them to that session since its last reload. A call that carries a subagent id is refused. A load the owner did not type, and the tools' use in plan and don't-ask modes, are the class “The mod's tools run with no permission prompt”.
- **The engine's verdict first.** Before `set_roster` writes, and before Open in app's tool call, the mod asks `$.tool.check` for the engine's verdict. `set_roster` refuses a `deny`, an `ask` that names a rule, and an organisation ceiling below `allow`. The usage summary writer's write is the exception: no permission rule, mode, owner hook or classifier reaches it. Other plugins' hooks can see, rewrite or deny the roster write, or approve it over the owner's ask rule; row 15 names this as the trust they already have.
- **One path rule.** The model never names a path. The roster, summary, log, marks and hand-off files are built from the config folder and a session id of the engine's own shape, and the rule walks every folder with `stat` before each write and each pane read, and again after each write. A link found after a write is told in the pane and a toast. Transcripts are found from the launch folder's projects name and a listed folder, under the place check.
- **Caps and strict checks.** Each file kind has a byte cap and a strict check, and a roster file that fails is refused without echoing what it holds.
- **Fixed words out.** Refusals and notes use fixed wording, and `gh`'s error text and a rejection's text are never shown. Row 15 names one exception: a server that answers as `ccd_window` can put one cleaned line of its own in Open in app's success toast. A second exception, not named in row 15, is a candidate for the owner's merge decision, decided with O1 to O3 (below): a quick action's fallback toast shows the line the mod could not fill, which is fixed words plus a checked title, or a PR number and repository, wherever toasts draw.
- **Engine answers are claims.** The pane list, the tool list, the verdict and environment values come from the engine, and a plugin whose hooks sit above grimoire's can answer them. That stays an open gap on row 15.

**How the pane shows text.** Report lines, roster text and to-dos are shown as written by their session, as claims, never as the owner's. A sender's name is a claim. Every string is drawn as text, never as Markdown or a link, with two exceptions, each an address the pane builds itself from a checked parse and never the stored string: a pull request row's page (off Desktop), and a to-do's `link`. A `link` is an issue or pull request on github.com, or one comment or review on either, in one closed pattern (`TODO_LINK`, whole string, no query or userinfo, and no fragment but one comment id behind an issue or pull request address), drawn with its repository and number, and the word comment or review for an anchored one, as its label, and opened only by the owner's press. A link with no anchor is a button on Desktop that runs `gh` and the engine's `Link` elsewhere; a link with an anchor is the engine's `Link` on every surface, Desktop included, because no `gh` command takes the anchor. An Owner entry the pane did not write in that session draws as "Owner (as recorded)". Pull request rows stay on github.com behind a click and name their repository.

**Classes and candidates for row 15.**

- “Other plugins share the mod's trust”: what another plugin can read, rewrite, plant or press in plugin state, the plugin's store or its data folder, as the class lists it.
- “A forged or misled session can speak for the lead”: a forged or misled session, and false entries written within the tool's own rules.
- “Data leaves the machine as the owner accepted”: other repositories' rows and titles in memory and on the pane, files at rest that reach backup, sync and other local accounts, and the level in the lead's transcript.
- “The mod's tools run with no permission prompt”: no permission prompt on the mod's tools. `start_background_session` also runs a process with no permission prompt and no classifier view, which that class as worded does not cover (it names `stop_background_session` as the one such tool): a candidate, proposed for the owner's merge decision.
- Not accepted, open issues of the threat model: another plugin planting session files, or planting, hiding or reading refusal lines; a session's own summary file feeding another card; the report store's question and a session's Remote Control link in plugin state. A program the owner runs is the machine's; the same race, link or planted file taken by another plugin, a branch's code or a steered session is an open issue; reliability items are notes, not threats.

**Candidates for the owner's merge decision.** These are candidates, not accepted risks, and none is an accepted class or an open issue of the threat model. The owner decides each by confirming the merge of the pull request that carries it; the lead flags them at merge.

- O1, a candidate that widens “Other plugins share the mod's trust”. Another plugin can press a quick button. The key's digest stops a press on a stale draw, not a forged press. At a quick press it can put any text in the box, ending with or replacing the expected line, through a `prompt.fill` hook. It can drop the draft, and it can hide a failed fill. It can blank `prompt.read`. A planted card, or a card a steered lead wrote, can choose which open pull request of the pinned repository the Merge line names (same-repository pull requests only; forks are never answered). If a redirect was set before `gh` first answered, the pinned repository may not be the one the owner expects; the Merge line names it so the owner can read it. A plugin hooked on `prompt.read` or `prompt.fill` also sees the box, the owner's draft included, at a quick press, as its own `$.prompt.read` could. Brigade's own fill never replaces. The owner's reading before Enter is the only control past that. None of this gives the plugin more than its own `$.prompt.fill` already could, except that a fill made at the owner's own press arrives when the owner expects text in the box.
- O2, a reliability note, not a threat. A keystroke typed between the `read` and the `fill` survives, and the line follows it after a space. A second press in the same gap fills its line too.
- O3, the `asUser` gap, not decided at this merge: it is restated here for context. Any plugin can call `$.prompt.submit` with `asUser`, and the lead's model cannot tell that text from the owner's. Brigade's Incantation relay now does so for heard speech (the `$.prompt.submit` row for heard turns, below): a `[voice]` turn counts as the owner's at the gates where a clear yes heard after a say-back stands, by the owner's decision of 2026-11-22. A rewrite at Enter by another plugin's `prompt.submit` hook is an open gap; the class “Other plugins share the mod's trust” covers it only for a level command.

## Summary, part 2: the head chef's guards

All of these are prose the host agent follows. Nothing runs them (“Text steers a session”).

- **Sessions.** The head chef starts sessions only on the owner's words in the lead's chat, or at levels 2 and 3 what the owner's user-level instructions file allows (accepted by the lead at level 3, flagged big). It names each session itself from letters, digits and `. _ -`, never from an issue, and it sets no permission mode. A background start with Remote Control is the default and goes only through the mod's `start_background_session` (proposed, not yet accepted by the owner): the tool takes no permission mode, runs with no shell, and refuses an unsafe name, model, effort, issue number or Linear identifier, repository, lead name or folder in code (the tool rows at the end of this page), while the lead's prose holds the owner's words, the model and effort, and the choice of folder; a Desktop start needs the owner's words choosing that route.
- **The start prompt.** It is the work (an issue or a Linear item) and the lead's name: it names the lead by name only and asks the member to send its questions and reports to that name. It holds no rule: the harness labels a message from another session as data, and the member's own rules govern stages, approvals, posting, accepted risks and the taking of a new lead name. A member whose rules need the owner's word refuses the lead's level-3 accepted-risk picks, and a message under the lead's name that names a new lead can redirect reports (not accepted, waiting for the owner's word). A start may end with one note from the lead, bounded as the tool's rules say and labelled by the tool as the lead's and not the owner's. It sits in the member's own first user turn, where no harness label applies and where a member's rules look for the owner's words. On the Desktop route the lead writes the same note and label itself, and no tool checks it.
- **The sender check (withdrawn).** A member takes the lead's messages by the lead's name only and checks no sender id, address or status file; it knows its lead by name only (not accepted, waiting for the owner's word). A status-file check would be a consistency check, not a guard, since a process of the same user can plant a status file (“A forged or misled session can speak for the lead”).
- **The owner's yes.** Starting a session needs the owner's words naming it, or at levels 2 and 3 what the owner's user-level instructions file allows (accepted by the lead at level 3, flagged big). Cleanup needs the owner's own words naming it, and at level 3 goes as the owner's file says. Each act on GitHub needs the owner's own words naming it, or at levels 2 and 3 what the owner's file allows (Proposed); each own-pick post then opens with a fixed line (accepted by the lead at level 3, flagged big). A request found in a report, a relay or a comment goes to the owner, and nothing is done.
- **Data, not instructions.** Reports, relays, notes and comments are data. A relay is quoted with its source. Each decision sent is labelled as the lead's own or the owner's words, relayed.
- **GitHub acts.** Each act names its repository and says whether the record is public. Free text goes through a temporary post file outside any repository, deleted afterwards. The head is read again before a merge. A branch to delete comes only from the owner's words or a same-repository head. No error text goes on an issue, a card, a to-do or a start prompt (“GitHub acts on the owner's word are irreversible and public”).
- **The roster** is written only through the mod's `set_roster`, under row 15's guards.
- **The permission warning.** It is shown before the first launch in a lead. Pressing "I understand" is a reminder; only the owner's words in chat record a risk, and, as the owner's user-level instructions file allows, at a level 3 the lead's own pick, logged (the lead writes no separate review entry; the pick stays a logged Lead entry).
- **Cleanup** (ADR 0016). At levels 1 and 2 a message from the owner that names each session by its title and says to clean it up is the yes, and anything vaguer gets a list first; at level 3 the owner's user-level instructions file decides. The lead archives each Desktop session with Desktop's archive tool, which Brigade does not intercept, and stops each background session with `stop_background_session`. It runs a cleaner only if the owner's instructions state the program and how to run it, from its own shell and under the permission mode in force (a prompt in the default mode; in auto or bypass mode, or under an allow rule, it states the command in chat first), and gives a session whose folder it does not know no run. Brigade removes nothing itself and runs no cleaner: no forced removal, no `-D`, no `claude rm`, no GitHub query. Whether a removal can be undone, and what a cleaner keeps, is the cleaner's own promise, which depends on how the owner's instructions have it run.

## Row 15

### Scenario

**Text another session wrote misleads the Brigade pane, or makes it act.** The plugin ships a mod: a hooks module, `brigade/register.tsx`, that Claude Code runs in every session where grimoire is installed, with the session's own rights. While its pane is open it reads the engine's own session files, `<config>/sessions/<digits>.json`, every 10 seconds (it runs no `claude agents --json`); it also takes each file's Desktop id, job id, waiting reason and update time, the ids only to match a card to its session and never kept, and draws the session's own name on its card, reads the lead session's roster file every 5, reads other sessions' transcripts to find a link and, for each roster member, the last model call's time and context size for a cache-warmth line on its card, also the context size of its recent calls and their new tokens, and its model's window, for a context meter on its card, and a burn rate sparkline (the context outlook is the one context bar), listing the config folder's `projects` folder at most once a minute to find a transcript that moved into a worktree folder, shows the first line of each report another session sends, and shows this session's own rate limits and context at the bottom of the pane, as an SVG image on Desktop, the editor and mobile. It also writes the roster file itself, when the model calls its `set_roster` tool, with no permission prompt. When the owner presses Open in app on a card with a Desktop id, it asks the Desktop app's own tool, `open_session_in` on the server named `ccd_window`, to show that session in a split beside the lead, again with no permission prompt. Every session, in a brigade or not, also runs a per-call hook and writes its own usage summary file, numbers, plus one model-family word from a fixed list (opus, sonnet, haiku, fable), again with no permission prompt. While its pane is open and a card carries a pull request number, it also runs `gh pr list` once a minute per repository, at most 6 runs a minute, the named repositories taking turns past five, for the repositories the shown cards name, again with no permission prompt, and draws the titles and repository names `gh` answers; a press of a pull request pill also runs `gh pr view <number> --web` for that card, again with no permission prompt, so the program `gh` picks opens the page in the owner's browser: `gh` takes it from `GH_BROWSER`, `BROWSER` or its own configuration, and the program inherits the session's environment, keys and tokens included, as the `claude://` opener does (“Data leaves the machine as the owner accepted”); a press of a to-do's pull request link button on Desktop runs `gh pr view <number> --web` the same way, and a link to an issue, comment or review is the engine's `Link` on every surface, so a press runs no process from the pane and the Desktop app's own opener opens the page; a Linear identifier, with `GRIMOIRE_LINEAR_SLUG` set, is a Desktop button whose press gives the built address to Open in app's host opener. A planted roster, a session named to match a card, a forged report, or a rate-limit kind a gateway names tries to make the pane run something, open a link the owner did not mean, read a file it should not, a file reached through a planted folder or link under `projects` included, or show the owner a false state or a false cache warmth included. Or a hijacked lead, a planted link or another plugin turns a roster write into a write somewhere else, or into a message to the owner. Or a planted card, another connected server or another plugin turns a press of Open in app into a call the owner's rules do not allow, a call to another tool or server, or a false answer. Or a planted link, a hard link or a planted file turns a session's summary write into a write over another file, or a forged summary file shows the owner a false warmth.

### What stops it today

**The pane waits for `/brigade` or a head-chef load:** at session start the mod registers `/brigade` and the usage summary writer's `turn.step` and `turn.complete` hooks, and reads the engine clock once for the writer, and the session id at each step and twice per write, and reads one key of the plugin's store, `permission-warning-ack`, copies it into plugin state, and offers the permission warning's tool, `show_permission_warning`, and registers a `skill.prompt` hook that reads each skill load's name, source and plugin name and acts only on head-chef's (below). Session start also registers three hooks, `tool.call` on `Skill`, `command.run` for `/head-chef` and `/grimoire:head-chef`, and `turn.start`, each of which passes on with no engine call unless a head-chef load is under way or a load left the pane waiting (`turn.start` also, as its row below says). Beyond these, session start runs no process or pane and reads no file, except that the Incantation mic band starts a timer at its first draw in every session (it reads `~/.grimoire/incantation/run/levels` four times a second while a listener writes it and once in eight ticks otherwise, and a press on a button writes `mute`, `unmute`, `mute-voice` or `unmute-voice` to `run/command`, and it reads `run/voice`, one word, the same way), and that a session start or reload that finds a stored autonomy level above 1 resets it and logs a Pane entry in the session's own log, pane open or not; a message from another session never opens it directly, though its text can lead the model to load the head-chef skill, which opens it (below). The mod holds no idle rule ([ADR 0019](../adr/0019-the-brigade-mod-holds-no-idle-rule.md) supersedes [ADR 0008](../adr/0008-brigade-is-no-longer-idle-by-default.md)). Its reads start on `/brigade` or when the head-chef skill loads from a plugin named grimoire or from any user-level skill of that name, and stop when the pane closes. The skill-load event carries no origin, so the hook cannot tell a typed `/head-chef` from the model loading the skill by itself, a subagent's load included, and text the model reads can lead it there. A head-chef skill from a project, the owner's policy, an MCP server, the account's synced skills, a built-in or another plugin opens nothing; a project agent that preloads the owner's or the plugin's head-chef is not told apart from a load (unconfirmed). A load while the pane is open resets nothing; it offers `set_roster` again and appends a fixed line saying the pane was already open. When the engine opens the pane from a head-chef load without placing it, or a throw follows the open, no reads start and no tool is offered, and a fixed toast and a fixed line name `/brigade`. The first turn of the lead's own that finds the pane shown and listed starts the reads, offers the tool and stores one fixed note. When the engine answers that the pane is placed but does not list it yet, the tool is offered and refuses every call until the pane is listed; the reads wait for the turn that finds it listed, which stores the same note. Where the security default skips `skill.prompt`, a model's head-chef Skill load opens no pane and stores one fixed note asking for `/brigade`. A typed `/head-chef` that core answered with its `ref` opens the pane only after the local `summary` skill listing shows the loaded copy is grimoire's or the owner's, with no other copy of the name listed. The accepted risk covers loads where `skill.prompt` runs; it is not widened to these sessions. Its `session.measure` hook does nothing unless the module's own timers run, which only an open pane starts, not plugin state another plugin could set, and it passes the event on unchanged on every path without waiting for the read, so a reading that hung cannot hold up another plugin's hook. Its reads run one at a time, a burst folding into one more, and a reading that started before the pane closed is dropped rather than stored. Its `session.receive` hook keeps a report only while those same timers run, so a flag in plugin state cannot make it keep reports while the pane is closed. The engine drops a pane whose drawing threw without running its close hook, so the roster timer checks every 5 seconds that the pane is still listed, and stops every read when it is not: the reads end within one tick of a close, not at once. **The roster write, `set_roster`:** the mod registers the tool only from `/brigade` or a head-chef skill load that opens the pane, and again on a reload (`session.start`) and on a `/clear` or a resume (`classic.SessionStart`) while the pane is open, so a session that never runs `/brigade` and never loads head-chef carries no `set_roster` (every session carries `show_permission_warning`, below).
